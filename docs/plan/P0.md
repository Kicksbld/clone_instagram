# Plan P0 — Socle

Découpage de la phase P0 en tranches verticales, selon [ADR-001](../adr/ADR-001-decoupage-phases-tranches-verticales.md) et la méthode de [ia-workflow.md](../ia-workflow.md).

**Règle d'usage** : on prend toujours la première tranche non cochée. Une tranche = une session IA, une branche, un commit. Elle n'est cochée qu'une fois la definition of done (`08` § 6) validée **sur la démo, sur iPhone**.

## Décisions de planification

- **Analytics regroupés en T11** : aucune tranche avant T11 n'intègre PostHog. T11 pose l'`AnalyticsService` (iOS) et le port `AnalyticsTracker` (API), puis ajoute les événements de toutes les tranches précédentes (onboarding, paywall, abonnement, post, like).
- **Suivre un compte privé en P0 : refusé.** Les demandes d'abonnement arrivent en P1 (`04` § 2.2) ; en P0, `PUT /users/{id}/follow` vers un compte privé est refusé (D32).

## Fiches

### T0a — Monorepo TypeScript, contrat, CI
- **Objectif** : la base de code TypeScript existe, démarre en local et passe la CI.
- **Sources** : `02` § 5-7 · `06` § 1-2, 5-6 · `07` § 1-2 · `08` § 2-4
- **ADR** : 002, 003, 004, 005, 007, 011
- **Contenu** :
  - workspace pnpm, TypeScript `strict`, ESLint + Prettier, scripts racine (`dev`, `lint`, `typecheck`, `test`, `build`, `contract:generate`, `db:migrate`, `db:seed`) ;
  - `packages/contract` : `openapi.yaml` avec `GET /health` et le schéma Problem Details, validation Redocly, génération des types ;
  - `packages/db` : configuration drizzle-kit, générateur UUID v7, encodage / décodage du curseur `(created_at, id)` ;
  - `apps/api` : Fastify, arborescence `modules/` + `shared/`, `main.ts`, validation de la configuration au démarrage, gestionnaire d'erreurs Problem Details, pino, dependency-cruiser, `/health` ;
  - `apps/worker` : connexion BullMQ, démarrage à vide ;
  - `apps/backoffice` : Next.js App Router, Tailwind, shadcn/ui, arborescence `features/`, client `openapi-fetch` ;
  - `supabase/config.toml`, `docker-compose.yml` (Redis), `.env.example` ;
  - GitHub Actions : contrat, lint, typecheck, test, build ;
  - `CLAUDE.md` de `apps/api`, `apps/worker`, `apps/backoffice`, `packages/contract`.
- **Tests** : `/health` via `fastify.inject` ; dependency-cruiser rejette un import interdit.
- **Hors tranche** : toute table métier, toute authentification.
- **Démo** : `supabase start`, `docker compose up -d`, `pnpm dev` → `/health` répond ; CI verte.

### T0b — Squelette iOS
- **Objectif** : le projet Xcode existe et parle à l'API via le client généré.
- **Sources** : `05` § 1-2, 5
- **ADR** : 003, 010
- **Contenu** : projet SwiftUI (cible iOS 26, Swift 6 strict, dossiers synchronisés) ; arborescence `App/ Core/ DesignSystem/ Features/ Resources/` ; configurations `Local` et `Demo` avec modèles `.xcconfig` ; `NSAllowsLocalNetworking` en `Local` seulement ; plugin `swift-openapi-generator` ; SwiftLint + SwiftFormat ; Nuke ; `ios/CLAUDE.md`.

- **Hors tranche** : authentification, écrans métier.
- **Démo** : le simulateur affiche l'état de `/health` local.

### T1 — Démo déployée + comptes SaaS
- **Objectif** : la démo tourne dès le début ; les configurations externes sont lancées.
- **Sources** : `02` § 6-7 · `09` § 2 et § 4
- **ADR** : 004, 009, 012, 013
- **Contenu** :
  - Supabase Cloud : projet démo, exposition du schéma `public` désactivée ou RLS sans policy, buckets `uploads` / `media-public` / `media-private` identiques au local ;
  - Railway : services `api` (Dockerfile + **pré-déploiement des migrations**), `worker` (Dockerfile avec ffmpeg), Redis ; variables d'environnement ;
  - Vercel : backoffice ;
  - déploiement automatique de `main` après CI verte ;
  - **lancés dès cette tranche** (configurations externes, prérequis de T10 et T11) : produit d'abonnement App Store Connect + sandbox, projet RevenueCat et entitlement `plus`, projet PostHog (région UE si possible), fournisseur Apple dans Supabase (CLI et Cloud).
- **Tests** : test automatisé « la clé publique Supabase ne lit aucune table ».
- **Démo** : l'iPhone en configuration `Demo` affiche `/health` de Railway ; le backoffice Vercel s'affiche.

### T2 — Inscription, connexion, onboarding
- **Objectif** : je crée un compte (email ou Apple), je choisis mon nom, mon username vérifié en direct, ma bio, puis j'arrive sur l'accueil.
- **Sources** : `01` § 4 · `02` § 3.1 · `03` § 4.1 · `04` § 2.1 · `05` § 3.6
- **ADR** : 003, 004, 005, 007, 010
- **Contrat** : `GET /me`, `GET /usernames/{username}/availability`, `POST /me/onboarding`
- **Base** : `profiles` (RLS sans policy)
- **Backend** : module `identity` ; vérification du JWT Supabase (`shared/infrastructure`) ; use cases `GetMe`, `CheckUsernameAvailability`, `CompleteOnboarding` (règles du username).
- **iOS** : `Core/Auth` (module `Auth` de `supabase-swift`, Sign in with Apple) ; middleware d'authentification du client API ; routeur racine (non connecté → auth ; sans profil → onboarding ; sinon accueil vide) ; feature `Onboarding` (un écran par étape, `OnboardingViewModel`).
- **Cas limites** : username pris (`409 username_taken`), format invalide, JWT invalide (`401`), profil absent (`404 profile_not_found`).
- **Hors tranche** : photo de profil (T3), analytics (T11), paywall (T10), statut suspendu / banni (T14).
- **Démo** : inscription email et Apple sur iPhone, onboarding complet, relance de l'app → directement sur l'accueil.

### T3 — Pipeline image + photo de profil
- **Objectif** : je choisis une photo de profil (onboarding ou modification du profil), elle est traitée et affichée.
- **Sources** : `02` § 3.2-3.3 · `03` § 4.4 · `04` § 2.1, 2.3 · `05` § 3.1 · `06` § 3-4
- **ADR** : 004, 007, 008
- **Contrat** : `POST /media/uploads`, `POST /media/{id}/complete`, `GET /media/{id}`, `PATCH /me`
- **Base** : `media` ; fonctions de transition de statut dans `packages/db`
- **Backend** : module `media` ; ports `MediaStorage` (Supabase Storage) et `JobQueue` (BullMQ) ; use cases `RequestUpload`, `CompleteUpload`, `GetMedia`, `UpdateProfile`.
- **Worker** : `process-image` (type réel, ≤ 20 Mo, WebP 150 / 640 / 1080 px, EXIF supprimé), `purge-orphan-media` (horaire) ; 3 tentatives, idempotence.
- **iOS** : `UploadManager` (URLSession background, HEIC → JPEG, 2 160 px max, attente par `GET /media/{id}`) ; étape photo de l'onboarding (passable) ; écran de modification du profil ; affichage via Nuke avec la bonne variante.
- **Cas limites** : média d'un autre utilisateur, transition invalide, fichier qui n'est pas une image, `purpose` incohérent, image avec EXIF GPS → sortie sans EXIF.
- **Hors tranche** : vidéo, événements WebSocket `media.ready` (P1), posts.
- **Démo** : changer sa photo sur iPhone, application mise en arrière-plan pendant l'upload.

### T4 — Profils + politique de visibilité
- **Objectif** : je vois mon profil et celui d'un autre (en-tête, compteurs, bio, relation).
- **Sources** : `03` § 4.2-4.3 · `04` § 2.1 · `05` § 4
- **ADR** : 005, 006, 007
- **Contrat** : `GET /users/{username}`
- **Base** : `follows`, `blocks` (utilisées par la politique)
- **Backend** : `shared/domain/visibility` complète (`canViewProfile`, `canViewContent`, `canViewStory`, `canMessage`, `isMutual`) avec tests unitaires ; use case `GetProfile`.
- **iOS** : feature `Profile` (le mien, un autre), grille vide pour l'instant.
- **Cas limites** : utilisateur bloqué → 404 dans les deux sens, compte suspendu → 404, compte privé non suivi → en-tête visible sans contenu.
- **Hors tranche** : suivre (T5), posts (T6a).
- **Démo** : ouvrir son profil et celui d'un compte du seed.

### T5 — Suivre, listes d'abonnés, recherche
- **Objectif** : je cherche un compte, je le suis ou ne le suis plus, je consulte les listes d'abonnés.
- **Sources** : `03` § 4.2, 6.2 · `04` § 2.1-2.2
- **ADR** : 005, 006, 007
- **Contrat** : `PUT` / `DELETE /users/{id}/follow`, `GET /users/{id}/followers`, `GET /users/{id}/following`, `GET /users/search?q=`
- **Base** : index trigramme sur `profiles.username` (`pg_trgm`), compteurs `follower_count` / `following_count`
- **Backend** : module `social` (`FollowUser` : refusé vers un compte privé en P0 (D32), `UnfollowUser`, compteurs via `UnitOfWork`), `ListFollowers`, `ListFollowing`, `SearchUsers` (visibilité appliquée).
- **iOS** : bouton Suivre optimiste avec retour arrière (pas de bouton Suivre sur un compte privé non suivi), listes paginées, onglet Recherche.
- **Cas limites** : se suivre soi-même, double follow, compte bloqué absent de la recherche, curseur invalide, suivre un compte privé (refusé).
- **Hors tranche** : demandes d'abonnement (P1), analytics (T11).
- **Démo** : rechercher, suivre, voir les compteurs changer.

### T6a — Publier un post photo
- **Objectif** : je choisis une photo, j'écris une légende, le post apparaît dans ma grille et s'ouvre en détail.
- **Sources** : `03` § 4.4-4.5 · `04` § 2.1, 2.4 · `05` § 3.1, 4
- **ADR** : 005, 006, 007, 008
- **Contrat** : `POST /posts`, `GET /posts/{id}`, `GET /users/{id}/posts`
- **Base** : `posts`, `post_media`, index `(author_id, created_at DESC, id DESC) WHERE deleted_at IS NULL`
- **Backend** : module `posts` (`CreatePost` : médias `ready`, du bon propriétaire, `purpose` `post`, jamais déjà attachés ; légende ≤ 2 200 ; `post_count`), `GetPost`, `ListUserPosts`.
- **iOS** : création (PhotosPicker, recadrage simple, légende), bandeau « Publication en cours », grille du profil, détail du post.
- **Cas limites** : média d'un autre utilisateur, `media_not_ready`, compte privé non suivi → 404, curseur invalide, rate limit 20 / h.
- **Hors tranche** : carrousel et suppression (T6b), likes (T8), commentaires (T9), mentions, reels.
- **Démo** : publier une photo depuis l'iPhone.

### T6b — Carrousel + suppression de post
- **Objectif** : je publie jusqu'à 10 photos dans un post, je supprime un de mes posts.
- **Sources** : `03` § 4.5 · `04` § 2.4
- **ADR** : 006, 007, 008
- **Contrat** : `POST /posts` (1 à 10 médias), `DELETE /posts/{id}`
- **Backend** : ordre `position` 0-9, suppression logique par l'auteur, décrément de `post_count`.
- **iOS** : sélection multiple, carrousel paginé dans le détail et la grille, suppression avec confirmation.
- **Cas limites** : 11 médias, suppression par un autre utilisateur (404), post déjà supprimé.
- **Démo** : carrousel de 3 photos, puis suppression.

### T7 — Feed d'accueil
- **Objectif** : je vois les posts des comptes suivis et les miens, du plus récent au plus ancien, avec un scroll fluide.
- **Sources** : `03` § 6 · `04` § 2.5 · `05` § 3.2, 3.5 · `06` § 5
- **ADR** : 006, 007
- **Contrat** : `GET /feed`
- **Backend** : module `feed`, requête Drizzle de `03` § 6.1 (blocages, auteurs non actifs exclus), validée par `EXPLAIN ANALYZE` ; **script de seed** (≈ 100 utilisateurs, abonnements, posts).
- **iOS** : feature `Feed` (`LazyVStack`, préchargement Nuke, variante `large`, tirer pour rafraîchir, pagination) ; profilage Instruments du scroll avec Liquid Glass.
- **Cas limites** : auteur bloqué absent, auteur suspendu absent, curseur invalide, feed vide.
- **Hors tranche** : bandeau de stories, reels.
- **Démo** : scroller le feed du seed sur iPhone.

### T8 — Likes
- **Objectif** : je like ou unlike un post (bouton ou double tap), le compteur réagit immédiatement.
- **Sources** : `03` § 4.6 · `04` § 2.4 · `06` § 2.4
- **ADR** : 005, 006, 007
- **Contrat** : `PUT` / `DELETE /posts/{id}/like` → `{ liked, likeCount }`
- **Base** : `post_likes`
- **Backend** : module `engagement`, `LikePost` / `UnlikePost` (visibilité, `UnitOfWork`, compteur incrémenté seulement si une ligne est insérée).
- **iOS** : mise à jour optimiste avec retour arrière, animation du double tap.
- **Cas limites** : double like, post invisible → 404, post supprimé.
- **Hors tranche** : liste des personnes ayant liké (P1), likes de commentaires (P1), notifications (P1).
- **Démo** : liker depuis le feed.

### T9 — Commentaires et réponses
- **Objectif** : je commente un post, je réponds à un commentaire (un seul niveau), je supprime mon commentaire.
- **Sources** : `03` § 4.6 · `04` § 2.4, 4
- **ADR** : 005, 006, 007
- **Contrat** : `GET` / `POST /posts/{id}/comments`, `GET /comments/{id}/replies`, `DELETE /comments/{id}`
- **Base** : `comments`, index `(post_id, created_at) WHERE parent_id IS NULL`
- **Backend** : `CreateComment` (≤ 2 200 caractères, réponse à une réponse refusée, `comment_count` / `reply_count`), `ListComments`, `ListReplies`, `DeleteComment` (auteur du commentaire ou du post, suppression logique).
- **iOS** : feuille de commentaires, réponses repliables, suppression par glissement.
- **Cas limites** : réponse à une réponse (`422`), commentaire d'un auteur bloqué masqué, rate limit 30 / min, curseur invalide.
- **Hors tranche** : likes de commentaires, mentions, notifications (P1).
- **Démo** : fil de commentaires avec réponses.

### T10 — Paywall Clone Plus
- **Objectif** : en fin d'onboarding et depuis les paramètres, je vois le paywall, j'achète en sandbox, l'API confirme mon plan `plus`.
- **Sources** : `02` § 3.7 · `03` § 4.13 · `04` § 2.1 · `05` § 3.7 · `06` § 2.5
- **ADR** : 005, 012
- **Prérequis** : produit App Store Connect et RevenueCat configurés (lancés en T1)
- **Contrat** : `POST /me/subscription/refresh`, champs `plan` / `plusExpiresAt` de `GET /me`
- **Base** : `subscriptions`
- **Backend** : module `billing`, port `SubscriptionProvider` + adapter REST API v2 RevenueCat, `RefreshSubscription` (pas d'appel si < 5 min), règle `isPlus` ; adapter en mémoire pour les tests.
- **iOS** : `purchases-ios`, `Purchases.logIn(profileId)`, feature `Paywall` (bouton « Plus tard », restaurer, gérer l'abonnement), Paramètres > Clone Plus, icône d'app alternative ; rafraîchissement après achat, restauration et au lancement ; fichier de configuration StoreKit.
- **Cas limites** : achat annulé, abonnement expiré, RevenueCat injoignable (dernier statut conservé), restauration sans achat.
- **Hors tranche** : avantages P1 (stories 48 h, vue anonyme, recherche dans les vues), webhooks, analytics et A/B test (T11).
- **Démo** : achat sandbox sur iPhone, icône d'app changée.

### T11 — Analytics + A/B test du paywall
- **Objectif** : les événements P0 (onboarding, paywall, actions principales) arrivent dans PostHog, et l'expérience attribue une variante qui change l'offre ou la présentation du paywall.
- **Sources** : `01` § 4, 6 · `02` § 3.7-3.8 · `05` § 3.6-3.8 · `06` § 2.5
- **ADR** : 005, 010, 012, 013
- **Backend** : port `AnalyticsTracker` + adapter `posthog-node` dans `shared` ; événements serveur `profile_created` (T2), `post_created` (T6a), `subscription_activated` (T10), envoyés après la validation de la transaction ; échec journalisé, jamais propagé ; adapter en mémoire pour les tests.
- **iOS** : `posthog-ios` ; `Core/Analytics` : protocole `AnalyticsService`, noms d'événements centralisés, `identify(profileId)` à la création du profil, `reset()` à la déconnexion ; événements `onboarding_step_completed` (T2), `paywall_viewed`, `purchase_started`, `purchase_completed`, `purchase_cancelled` (T10) et actions principales (post, like, abonnement) ; `PaywallViewModel` lit la variante du feature flag d'expérience et choisit l'offre RevenueCat ; variante par défaut si PostHog est injoignable.
- **PostHog** : feature flag d'expérience à plusieurs variantes, métrique principale `purchase_completed`.
- **Tests** : choix de l'offre selon la variante, variante par défaut, PostHog injoignable (non bloquant), aucune donnée personnelle dans les propriétés.
- **Hors tranche** : affichage des résultats dans le backoffice (T16).
- **Démo** : parcours complet sur iPhone, l'entonnoir apparaît dans PostHog ; deux comptes voient deux variantes.

### T12 — Paramètres, blocage, signalement
- **Objectif** : je passe mon compte en privé, je bloque ou débloque un compte, je consulte ma liste de bloqués, je signale un post, un commentaire ou un compte.
- **Sources** : `01` § 4 · `03` § 4.2, 4.12 · `04` § 2.1-2.2, 2.8
- **ADR** : 005, 006, 007
- **Contrat** : `PATCH /me/settings`, `PUT` / `DELETE /users/{id}/block`, `GET /me/blocks`, `POST /reports`
- **Base** : `reports`
- **Backend** : `BlockUser` (supprime les abonnements dans les deux sens et met à jour les compteurs, `UnitOfWork`), `UnblockUser`, `ListBlocks`, `UpdateSettings`, module `moderation` : `CreateReport`.
- **iOS** : écran Paramètres (compte privé, bloqués), menus « Bloquer » et « Signaler » sur profil, post et commentaire.
- **Cas limites** : compte bloqué invisible partout (profil, feed, recherche, commentaires : tests de non-régression), rate limit signalements 10 / h, se bloquer soi-même.
- **Hors tranche** : demandes d'abonnement et acceptation automatique au passage en public (P1).
- **Démo** : bloquer un compte et vérifier qu'il disparaît du feed et de la recherche.

### T13 — Suppression du compte
- **Objectif** : je supprime mon compte depuis l'app ; l'accès est coupé immédiatement, puis données et fichiers sont purgés.
- **Sources** : `01` § 6 · `03` § 4.1, 4.13 · `06` § 3
- **ADR** : 007, 008, 012, 013
- **Contrat** : `DELETE /me`
- **Backend / worker** : suppression de l'accès, job `purge-account` (données, fichiers, client RevenueCat, personne PostHog ; appels idempotents).
- **iOS** : confirmation dans Paramètres, rappel de résilier l'abonnement Apple, `reset()` analytics et déconnexion RevenueCat.
- **Cas limites** : purge rejouée sans erreur, RevenueCat ou PostHog injoignable pendant la purge.
- **Démo** : supprimer un compte de test, vérifier que son profil renvoie 404.

### T14 — Backoffice : connexion admin + utilisateurs
- **Objectif** : un admin se connecte, recherche un utilisateur, consulte sa fiche, le suspend, le bannit, le réactive ou le supprime.
- **Sources** : `02` § 3.1 · `03` § 4.1, 4.12 · `04` § 2.9 · `07`
- **ADR** : 005, 011
- **Contrat** : `GET /admin/users`, `GET /admin/users/{id}`, `POST /admin/users/{id}/suspend` · `/ban` · `/reactivate`, `DELETE /admin/users/{id}`
- **Base** : `admin_roles`, `admin_audit_log` ; script de création d'un admin
- **Backend** : vérification du rôle admin dans chaque use case, écriture dans `admin_audit_log`, **refus des écritures d'un compte suspendu ou banni** (`403`).
- **Backoffice** : connexion (`@supabase/ssr`, refus des non-admins), pages utilisateurs (recherche, fiche avec abonnement Plus), actions avec motif obligatoire ; chaque Server Action revérifie la session.
- **Tests** : Playwright (connexion admin, refus d'un non-admin, bannissement).
- **Démo** : suspendre un compte, puis vérifier sur l'iPhone qu'il ne peut plus publier.

### T15 — Backoffice : modération
- **Objectif** : un admin traite un signalement : suppression du contenu ou classement.
- **Sources** : `02` § 3.5 · `04` § 2.9 · `07` § 4
- **ADR** : 008, 011
- **Contrat** : `GET /admin/reports`, `GET /admin/reports/{id}`, `POST /admin/reports/{id}/resolve`
- **Backend / worker** : `ResolveReport` (suppression logique du contenu, audit, job `purge-content-files`).
